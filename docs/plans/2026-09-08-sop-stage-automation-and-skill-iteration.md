## 1. 目标与设计边界

建立两个相互连接的闭环：

1. 执行闭环：启动 SOP → 进入阶段 → 智能体执行 → 提交产物 → 验收与审核 → 推进下一阶段。
2. 改进闭环：运行证据 → 样例与反馈 → skill 候选版本 → 对照评测 → 审核发布 → 观察与回滚。

阶段输入输出契约是两个闭环共同的验收依据。自动推进、产物标准、skill 评测应一起设计，避免先让流程跑起来，再用自由文本猜测是否完成。

本稿中的“训练”暂指平台内对 skill 指令、示例、脚本及参考资料的持续改进，不预设需要模型参数训练。模型微调保留为后续独立方向，需要另行明确数据授权、模型供应商、训练成本和部署方式。

以下设计是建议方案，不表示这些能力已存在或已经最终确认。表名、字段名与接口职责也是设计候选，实施前需要结合最新代码细化。

### 2.2 两种 Stage 必须区分

- issue.stage：父 issue 内部的数字阶段；阶段屏障关闭后可唤醒父任务智能体。
- workflow_instance_stage：SOP Run 内正式阶段；承载计划、审核和输入输出要求。

前者可以在某个 SOP 阶段内部组织工作，但不能充当整个 SOP 的状态机。两个层级同时存在时，子任务通知负责阶段内部协调，SOP 服务独占正式阶段推进权限，防止重复派工。

## 3. 目标架构与职责

| 角色 | 职责 |
| --- | --- |
| 阶段执行智能体 | 理解目标、执行或拆分工作、汇总结果、提交产物 |
| 阶段审核者 | 根据契约和证据做审核，可以是智能体或成员 |
| WorkflowExecutionService | 创建轮次、派工、检查条件、处理决策、推进与恢复 |
| Skill 评测服务 | 使用固定样例评估候选版本，保留评分与证据 |
| 发布负责人 | 审核 skill 候选版本和 SOP 契约变更，控制生产采用版本 |

第一版由后端根据 SOP 顺序确定下一阶段，不强制引入全流程总控智能体。复杂拆分交给阶段执行者。

执行顺序：

1. 启动 Run，固定计划版本、skill 修订和契约版本。
2. 为当前阶段创建执行轮次，解析并快照输入。
3. 输入校验通过后，创建阶段主 issue 并派发执行任务。
4. 执行者可创建当前轮次的子 issue；提交结果与产物清单。
5. 后端检查必需任务、产物与验证证据，满足后进入审核。
6. 审核通过，原子地完成当前轮次并建立下一阶段派工意图。
7. 最后一个阶段通过后完成 Run；失败则阻塞、重试、返工或回退。

## 4. 阶段配置与执行模型

### 4.1 配置

| 配置 | 初始建议 |
| --- | --- |
| execution_mode | manual 或 agent；默认保留现有手动行为 |
| executor | 自动阶段明确指定智能体；后续扩展 Squad 和实例默认值 |
| instructions | 阶段目标、范围、约束与执行说明 |
| input_spec / output_spec | 版本化结构与验收要求 |
| input_bindings | 将 Run 输入、前序产物或项目资源映射到输入字段 |
| required_skills | 固定 skill 修订与依赖；复用并完善已有快照 |
| completion_rule | 必需任务完成、结果已提交、产物有效等明确规则 |
| gate | none、human、agent、hybrid |
| retry_policy | 技术重试上限、超时、退避策略 |
| rework_policy | 返工次数、回退目标、人工接管条件 |

执行者与审核者独立。gate.decider 不能隐式承担执行者职责。@self 必须在轮次创建时解析成该轮次实际执行智能体。

### 4.2 执行轮次

建议增加 workflow_stage_execution，记录工作区、Run、阶段、轮次、计划修订、配置快照、执行者、主 issue、输入快照、状态、结果、开始结束时间和失败原因。

建议状态：pending → queued → running → awaiting_review → succeeded；异常分支为 blocked、failed、cancelled。审核子状态区分等待智能体与等待人工。

一次业务返工产生新轮次；同一轮次内可以有多次智能体调用。任务执行成功、issue 完成、阶段通过是三个独立事实。

队列运行、issue 归属记录、产物与决策必须关联轮次。历史不能仅依赖 issue 当前的阶段字段；移动 issue 不能改变过去的执行归属。

技术重试保留业务轮次但增加调用尝试；回退和返工创建新轮次。任何情况下都不能复用旧轮次的通过决策。

## 5. 输入输出契约与产物标准

### 5.1 契约的四个部分

| 部分 | 内容 | 校验方 |
| --- | --- | --- |
| 结构 | 字段、类型、必填、枚举、文件类型和数量 | 后端结构校验器 |
| 业务约束 | 单位、范围、跨字段关系、前置条件 | 确定性校验器或审核者 |
| 质量要求 | 完整性、正确性、证据充分程度 | 测试、领域工具、审核者 |
| 交接规则 | 来源绑定、产物版本、后续消费者 | 编排服务 |

第一版采用受限的版本化 schema 和显式绑定，拒绝不支持的规则，不引入任意代码表达式求值。配置界面显示字段和自然语言说明，技术 schema 放在高级配置中。

### 5.2 输入规范

- 每个输入声明名称、类型、是否必填、描述和来源。
- 来源可以是用户提供的 Run 输入、指定前序阶段的已验收产物或明确的项目资源版本。
- 不通过全文评论历史猜测正式输入；评论可作为补充上下文。
- 大文件传递受权限保护的资源引用，不放进数据库 JSON 或全部塞进 prompt。
- 开始轮次时解析并固定具体版本；输入缺失或不兼容时进入 blocked，明确列出缺项。
- 回退后重新选择当前有效产物并建立新快照，不静默使用过期下游结果。

### 5.3 输出规范

阶段结果应包含 summary、outputs、evidence、blocked_reasons；身份、轮次和版本由服务端验证或补齐，不能信任智能体自行声明。

产物清单至少记录：

| 字段 | 说明 |
| --- | --- |
| artifact_id / revision | 产物稳定身份及不可变版本 |
| kind / media_type | 文档、数据、代码变更、报告等类型及实际格式 |
| storage_ref / checksum | 存储引用和可校验内容摘要 |
| schema_version | 采用的结构规范版本 |
| producer_execution_id | 产生该版本的阶段执行轮次 |
| source_artifact_revisions | 依赖的上游产物版本 |
| validation_results | 验证器版本、结果、时间和证据引用 |
| review_status | 当前版本的审核结果 |

Markdown/PDF 报告可以供人阅读，但有下游计算需求时同时提供 JSON/CSV 等结构化数据。代码产物记录仓库、提交或变更引用和测试证据；仅一句“已完成”不能作为交付。

产物清单作为现有存储之上的业务元数据，不另建一套文件上传和权限系统。外部可变链接需要保存版本或摘要，无法固定时标明不可复现。

### 5.4 示例：需求 → 方案 → 验证

| 阶段 | 输入 | 输出 | 通过标准 |
| --- | --- | --- | --- |
| 需求澄清 | 用户目标、约束、原始资料 | 需求说明、结构化验收标准、待确认项 | 必填项齐全，关键待确认项清零，人工确认 |
| 方案设计 | 已验收需求版本、项目资源 | 方案文档、参数或任务清单、风险说明 | 需求可追溯、参数带单位、方案审核通过 |
| 执行验证 | 已验收方案版本、执行环境 | 原始结果、验证报告、失败项 | 验收项逐条有结果与证据，关键项全部通过 |

具体业务可以扩展仿真模型、边界条件、网格、收敛报告等产物，但应通过领域契约包表达，不写死到通用 Workflow 服务。

### 5.5 审核与失效

- none：完成规则满足后由服务端推进。
- agent：自动派发指定审核智能体，并接受结构化决策。
- human：等待指定成员审核。
- hybrid：智能体通过后再等待人工通过，二者必须针对相同结果版本。
- 审核后修改结果、必需任务或影响验收的输入，会使相关决策失效。
- 空阶段不能因开放任务数为零自动通过；必须提交结果，或明确声明允许空阶段。
- cancelled 表示不再等待，不默认代表成功交付；必需任务取消需要阻塞或显式豁免。

## 6. 平台内 Skills 训练与迭代

### 6.1 skill 作为可评测的版本化能力包

建议一个发布修订包括 SKILL.md、引用资料、脚本、正反例、契约引用、工具依赖和内容摘要。评测样例与报告关联该修订，但保留集不交付给执行智能体。

skill 描述通用执行方法；Stage 定义本次业务目标、参数和产物要求。skill 声明支持的契约版本，阶段发布时检查兼容性。一个 Stage 可以使用多个 skill，记录组合与依赖顺序。

### 6.2 训练迭代流程

1. 收集反馈：从失败轮次、审核驳回、人工修正和优秀产物中选择样例。
2. 整理样例：保存输入快照、预期约束、评分规则、结果与失败标签，记录来源和使用权限。
3. 分析原因：区分 skill 指令问题、输入不足、工具故障、契约问题和模型能力问题。
4. 创建候选：人工或改进智能体提出新修订，展示内容差异和改进假设。
5. 对照评测：在固定环境和相同样例上运行基线与候选，保存全部结果和消耗。
6. 审核发布：负责人检查回归、改进证据和成本，选择是否发布。
7. 观察效果：对新 Run 定向采用候选版本，跟踪生产指标，必要时回滚后续采用版本。

不能把一次运行成功自动记成高质量样例，也不能把所有失败都归因于 skill。未经筛选的运行轨迹不直接成为全工作区共享训练数据。

### 6.3 评测设计

| 维度 | 示例指标 |
| --- | --- |
| 契约符合度 | 输出结构通过率、必需产物齐全率 |
| 业务正确性 | 验收项通过率、领域验证器结果 |
| 流程遵循 | 必需工具步骤、阶段归属、证据可追溯性 |
| 稳定性 | 多次重复运行的成功率及波动 |
| 人工负担 | 驳回率、人工修改量、返工次数 |
| 成本与时延 | token、工具调用、耗时及单位成功成本 |

每个评测集固定版本，分为改进集、回归集和保留集。改进智能体不读取保留集答案；评分规则与验证器也固定版本。确定性验证优先，模型评分需记录评分智能体及依据，并对争议样例人工复核。

阈值按具体 skill 定义，第一版不宣称统一分数等于可发布。关键检查全部通过、无关键回归，再比较质量和成本。对具有随机性的任务做重复运行，展示样本数与波动。

评测使用隔离目录和测试资源，限制实际外部写入，设置调用预算、并发上限和超时。工具返回可使用固定样本或测试环境；报告明确哪些验证基于模拟、哪些经过真实环境验证。

### 6.4 版本与发布

- skill 修订内容不可变；发布指针与内容版本分离。
- 新 Run 固定发布修订；运行中不因 skill 发布而热更新。
- 升级现有 Run 必须显式记录计划变化，校验契约兼容性，并对受影响阶段创建新轮次。
- 回滚影响后续版本选择，不重写历史产物、运行证据或审核记录。
- 内置 skill、工作区 skill、运行时本地 skill 的版本身份与编辑权限在专项设计中统一；现有快照机制作为基础。

### 6.5 产品入口

建议在 skill 详情增加“版本、样例、评测、反馈”，在 SOP 阶段配置中展示选用修订及契约兼容性，在 Run 中提供“将本次结果加入评测样例”。

改进智能体可生成候选修订和失败分析；发布权限由负责人控制。先实现单个 skill 的对照评测，再扩展多 skill 阶段评测与完整 SOP 回放，避免无法判断效果来自哪一层。

## 7. 可靠性、权限与状态边界

1. 将阶段切换规则集中到 WorkflowExecutionService，人工接口和自动推进共享实现。
2. 锁定 Run 或条件更新，校验预期阶段、执行轮次、计划与结果版本；现有切换路径需要补齐这一点。
3. 状态变化与派工意图同事务提交；消费者通过唯一键幂等派工，后台扫描补偿遗漏。
4. 任务新增、移入移出、取消、重新打开均会改变屏障，需要共享并发控制规则，不能只监听 done。
5. 暂停停止新派工；明确在途任务是否继续。旧回调可保留日志，但不能在暂停或失效后推进。
6. 未来阶段可以预建 issue，但不得提前自动执行；用户主动搁置的工作不能被静默激活。
7. 队列领取及结果提交验证轮次仍有效；归档、取消、权限撤销和旧轮次回调不能绕过控制。
8. 智能体只能提交被授权轮次的结果和决策；审阅权限、执行权限与计划修改权限分开。
9. 工作区隔离覆盖产物、样例、评测与 skill 版本；复用现有归因，明确启动者和责任人。
10. 不新增数据库外键或级联操作；清理由应用事务处理。所有新增索引使用独立单语句的 CONCURRENTLY 迁移。

## 8. 候选数据与服务边界

| 对象或服务 | 职责 |
| --- | --- |
| workflow_stage_execution | 阶段轮次、状态与快照 |
| 阶段动作持久化记录 | 派工、审核、推进的恢复与去重；优先评估复用现有机制 |
| artifact / artifact_revision | 产物清单、来源与不可变版本；内容复用现有存储 |
| workflow_gate_decision 扩展 | 关联轮次、结果版本、证据与审核步骤 |

| skill_evaluation_case / suite | 样例、数据集版本、评分规则 |
| skill_evaluation_run | 基线/候选、运行环境、逐样例结果与汇总 |
| WorkflowExecutionService | 阶段状态机、条件判断、派工与恢复 |
| 契约与产物校验服务 | 结构、资源引用及领域验证器结果校验 |
| SkillEvaluationService | 批量运行评测、比较与报告 |

API 能力需要覆盖启动、暂停/恢复、结果提交、审核、重试/返工、执行历史、产物读取、skill 修订和评测。CLI 与内置 skill 文档同步提供智能体可调用的结果提交和审核协议。

前端服务端状态由 packages/core 的 React Query 管理；共享界面放 packages/views，Web/Desktop 仅做平台接线。所有新增响应使用 schema 解析，兼容旧 Desktop 的缺字段和未知枚举。移动端语义需在实施评审中核对，具体界面范围另定。

## 9. 分阶段实施计划

| 阶段 | 工作内容 | 验收结果 |
| --- | --- | --- |
| P0：规范与样板 | 选一个真实 SOP；定义术语、阶段契约、产物样例、审核规则和阶段交接包；核查 skill 版本和存储能力 | 一个完整 SOP 从输入到最终交付均可说明并校验；形成正常、失败、返工样例及版本交接示例 |
| P1：最小执行闭环 | 执行配置、轮次、持久化派工、阶段就绪检查、产物清单与预检、服务端验收、版本交接、none/human 审核、暂停恢复 | 点击启动后自动执行并交付产物；下一阶段收到已验收的具体版本；缺少必需产物或能力时明确阻塞；中断可恢复 |
| P2：审核与返工 | agent/hybrid 审核、动作审批与阶段审核分离、结果版本、回退返工、旧结果失效、未来阶段执行约束 | 全智能体链路可推进；动作获准不能替代产物验收；混合审核不能跳过人工；旧轮次不能放行新轮次 |
| P3：Skills 改进闭环 | 反馈分类、知识与 skill 改进提案、不可变修订、样例集、基线与候选评测、报告、人工发布及回滚 | 改进可追溯到来源轮次与原因；平台内完成一次有证据的 skill 改进，新 Run 可采用新版本，旧 Run 不受影响 |
| P4：扩大范围 | 多 skill 组合评测、SOP 回放、领域验证器、Squad 与条件分支 | 能评估组合效果、接入更多业务；以样板效果决定投入顺序 |

P0 的 skill 版本与评测数据设计可以和 P1 实施并行推进；P1 必须保留输入、产物与执行证据，为 P3 提供数据。第一版不实现通用 DAG、自动模型微调或无审核的 skill 自动发布。

### 9.1 验证清单

- 两阶段 SOP 自动派工、结果校验、人工审核与最终完成。
- 空阶段、缺产物、必需任务取消不能误通过。
- 同一完成事件重复、并发审核和 Worker 重启不会重复推进或派工。
- 状态提交后进程退出仍能补偿派工；暂时离线与永久失败可区分。
- 回退后旧结果与旧审核失效；重开或新增任务不会与通过竞态。
- 暂停、取消、权限撤销、未来阶段任务及迟到回调符合控制规则。
- 审核只针对当前结果版本；hybrid 两个审核步骤均被满足。
- 本地产物预检通过后，服务端仍能拒绝不符合阶段契约的提交；下一阶段只接收已验收版本。
- 动作审批、阶段审核和 skill 发布决策各自生效，不能相互替代。
- 改进提案保留来源轮次、证据、理由和适用范围；环境故障不自动触发 skill 改写。
- skill 新修订不热更新旧 Run；评测固定版本、保留集隔离、回归可定位。
- 默认测试使用假的智能体执行程序；真实智能体评测通过显式启动并记录消耗。
- 新 API 包含异常响应解析验证，共享界面覆盖 Web/Desktop 接线。

## 12. Silieco 从 AgentSpace 借鉴的设计

### 12.1 分析范围与结论

阅读了 [AgentSpace 中文说明](https://github.com/HKUDS/AgentSpace/blob/main/README_ZH.md)，并静态检查 main 在 2026-09-08 获取到的提交 0f9da1b125def4d5a0d05b34bf7c5cec0686bbf2。未安装依赖、启动服务或执行其测试；以下结论不代表生产可靠性评估。

AgentSpace 的可借鉴价值集中在工作空间内的产物回收、步骤交接、知识候选审核与统一运行协议。Silieco 已有 issue、SOP 模板、阶段副本、运行队列及技能快照，适合将这些机制接入现有模型，不需要整体引入另一套工作空间或运行框架。

本节服务于 Silieco 的开发决策，仅记录我们采用的设计思路、适配方式与实施要求。借鉴项已纳入第 9 节计划，具体 API 和数据结构继续迭代。

### 12.2 具体借鉴点

| 机制 | AgentSpace 已检查的实现 | Silieco 建议 |
| --- | --- | --- |
| 产物清单 | runtime-output 中分别描述附件、文档、知识候选等输出，带预览、验证及文件边界检查 | P1 增加阶段结果清单和提交前校验；本地预检与服务端验收共享语义，服务端仍做权威校验 |
| 依赖与交接 | ChannelDocumentRunStep 记录依赖步骤、队列任务、文档及文档版本；完成后为就绪步骤派工 | 将同样的显式交接落实为 accepted artifact revision → next input binding |

### 12.3 不能直接等同或照搬的部分

1. 文档协作步骤不等于版本化 SOP 阶段。检查到的步骤模型没有覆盖本文要求的阶段返工轮次、完整输入输出契约和结果版本审核。
2. completed_with_warning 允许依赖步骤继续；缺少新文档版本也可能进入这个状态。Silieco 必须区分非必需项警告与必需产物缺失，后者不得自动通过。
3. 产物清单校验文件与格式，不等于验证领域结果正确；仍需要阶段契约、业务验证器和验收证据。
4. 知识提案审核不等于 skill 训练。已检查的 skill、知识提案模块未发现完整的基线/候选评测、保留集、回归门槛和发布效果比较闭环；不据此断言整个仓库绝无相关能力。
5. AgentRouter 接受调用方明确给定的 harness，承担适配与归一化；不能仅凭 Router 名称推断其实现了按任务质量/成本学习最优运行时的调度算法。
6. 不直接照搬领域存储或状态修改方式。Silieco 的 Go、sqlc、React Query 边界与并发、幂等要求仍以当前项目规范为准。

### 12.4 Silieco 落地清单

| 借鉴项 | Silieco 实施要求 | 阶段与验收 |
| --- | --- | --- |
| 结构化产物清单 | 提供统一结果提交入口，关联轮次、契约版本、文件引用和验证证据；支持提交前预检，服务端再次校验 | P0 定义格式，P1 实现；缺少必需产物不得通过，界面可定位具体缺项 |
| 显式版本交接 | 阶段交接包包含输入快照、产物清单、已验收版本与证据；下一阶段通过 input_bindings 解析具体版本 | P1；不依赖评论推断输入，不读取可变的“最新版本”，回退后重新建立有效绑定 |
| 可审核的改进提案 | 记录来源轮次、产物证据、问题分类、改进理由、内容差异和适用范围；区分知识更新、skill 改进、契约修改与环境故障 | P3；skill 提案进入候选评测，知识提案经审核沉淀，原始反馈不能直接覆盖正式版本 |
| 分层审批 | 动作审批关联具体操作，阶段审核关联轮次与结果版本，发布审核关联 skill 修订及评测报告；可在统一待办入口展示 | P2 实现动作/阶段分离，P3 接入发布审核；三类决策不能相互替代 |
| 就绪检查与诊断 | 在现有 TaskService、守护进程和 Go 适配层检查执行者、运行时、skill、工具及授权；记录结构化原因和恢复建议 | P1；区分暂时离线、缺少能力、权限不足与执行失败，为人工处理和后续评测提供可靠分类 |

这些借鉴通过 Silieco 现有服务、存储与前端边界实现。先交付一个可验证的 SOP 闭环，再扩展知识治理与复杂调度；不因参考项目的功能范围扩大本计划。
