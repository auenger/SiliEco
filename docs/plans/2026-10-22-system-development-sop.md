# 系统研发 SOP

App 的内置 SOP 模板新增「系统研发 SOP」，Web 与 Desktop 使用同一份模板。创建 SOP 时可直接选择模板，编辑并发布到 Space；Project 可按现有入口创建变体、启动运行。

## 四个阶段

| Stage | 目标 | 主要 Markdown 产物 |
| --- | --- | --- |
| 需求的输入和整理 | 保留原始材料，结合项目上下文明确范围、需求和验收条件 | requirements.md、source-index.md、open-questions.md |
| 需求转研发设计 | 形成具体方案、依赖清晰的研发任务与测试计划 | development-design.md、development-tasks.md、test-plan.md |
| 研发任务实现 | 按确认方案实现，提供代码、自测结果和运行交接 | 代码及必要配置、implementation-notes.md |
| 研发任务本地测试和验收 | 在本地逐项验证验收条件，保留证据并确认结论 | verification-report.md、acceptance-summary.md |

## 产物目录

四个 Stage 的输出要求均明确：Markdown 产物实际写入 Project 绑定的项目目录，优先遵循已有文档规范；没有约定时使用 `docs/features/<需求或任务标识>/`，各阶段沿用同一需求目录。在 Task 中记录相对项目根目录的产物路径、用途及版本或更新时间，通过相对链接关联前置产物；更新前检查已有文件，避免覆盖其他需求或运行的文档。项目目录不可用时记录阻塞，不能将聊天回复视为文件已交付。

## 内容与执行约定

- 每个 Stage 的描述包含「阶段目标」和「执行内容」；输入标准说明交接材料与所需项目上下文，输出标准说明必交产物与完成条件，均为多段 Markdown。
- 需求与验收条件分别编号为 REQ、AC，建立原始材料、设计、任务、实现和验证证据的追溯关系。
- 项目目录由执行者按实际权限读取；无法访问、无法解析的材料必须列明缺口。模板本身不承诺自动解析所有 Office 文件或自动获取目录权限。
- 设计确认与最终验收启用人工 Gate；默认执行模式沿用现有模板逻辑，不预设执行 Agent 或强制绑定 Skill。创建后可按项目选择合适的执行者与 Skill。
- 实现与验收阶段包含 blocked 状态；验收失败按既有运行调整/回退入口返回实现，保留问题和复测证据，不额外增加 Stage。
- 模板中的文件名是交付约定，执行者需要实际生成并关联产物；模板不会仅因选择就自动生成文件、创建子 Task、推送代码或部署服务器。

## 验证

ProjectSopDesigner 组件测试 16 项通过，包含四阶段顺序、发布后的 Markdown 描述与输入输出、相邻阶段产物交接及人工 Gate 的验证；views TypeScript 类型检查通过。
